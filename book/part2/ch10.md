# Chapter 10 — Simplicity: The Art of Doing Less

Every system is a snowball rolling downhill: features accrete, dependencies multiply, "one small config" becomes eleven nested layers, and someone keeps a gorgeous diagram of a pasta bowl labeled with the word "architecture."

The classic book devoted an entire chapter to **simplicity**. In the AI era it needs a shrine. Because here's the 2026 secret that most teams are still learning the expensive way:

> **AI makes it effortless to build complexity, and effortless complexity is a reliability tax you pay forever.**

An AI coding agent will happily scaffold you a 14-service microservices salad for a task a cron could do. An AI agent will cheerfully add "a caching layer we don't need yet." The machines are not on the side of simplicity — you have to be.

## Why simplicity is a reliability feature

Every moving part is a place to break:

- More services → more networking → more failure points, more to observe, more to trace.
- More config → more chances to misconfigure, more drift, more "it worked on Tuesday" moments.
- More dependencies → longer tails, harder triage, more supply-chain exposure.
- More code → more bugs and — in the AI era — more *output* for agents to review.
- More moving parts = a bigger box for an AI agent to reason about when it's your on-call.

Complexity degrades *predictability*, and predictability is what makes both humans and agents safe. A simple system is easier to test, easier to run, easier to automate, easier to make autonomous safely, **and easier for an AI to explain** — which in 2026 means everything.

## The classic simplicity toolkit (still the whole game)

1. **Do the least thing that works.** Not the most impressive; the least correct.
2. **Boring technology is better technology.** The unglamorous, well-understood solution wins. Newness is a defect unless there's a reason. (Especially in 2026: "AI" is not a reason to use AI.)
3. **Delete things.** Code deletes, config slugs deleted, features deleted. Nothing in production should be a souvenir.
4. **Make it legible.** If a newcomer (or an agent) cannot read the topology in an hour, it's a maze, and mazes tax you in incidents. (Your AI teammate's ability to "understand" your infrastructure is capped by its legibility.)

## The 2026 additions: two new enemies, two new habits

### New enemy #1 — "AI sludge": generated complexity
Agents generate code, configs, YAML, and "architectures" at cosmic speed. Much of it is *fine*. Some is elegant. A lot is **AI sludge**: plausible, over-engineered, duplicate-laden, and undocumented. Worse, it compounds: agents trained on sludge-saturated repos generate more sludge.

**The anti-dote:** review gates with a *simplicity checklist*: *"Could a script/prism do this instead of a service?" "Is this YAML telling three different stories?" "Does this prompt need 4k of context?"* — and an explicit *SLOC-and-services diet* enforced, not vibed: limit services/config entropy per product; sunset the sludge quarterly.

### New enemy #2 — accidental memories
Every new dependency is a supply-chain door (Chapter 29) and every AI *context/memory appendage* is state you must keep trustworthy (Chapter 19). The "memories" your agents accumulate are moving parts in the machine of trust. Simple memory = trustworthy memory.

### New habit #1 — Complexity is a metric
Track it like you track latency: **services per product, config files per service, dependencies per repo, pending-review queue size, prompts per feature, agent tools per scope.** When a chart triples in a quarter, that's the alert you should treat as a pager page. Watch your "complexity budget" the way you watch your error budget — spend it on purpose, cut it with discipline.

### New habit #2 — AI-assisted *simplification*, deliberately pointed at itself
The same agents that create sludge can grind it down *when told to*. A standing quarterly task: **"find five things to delete whose deletion a reviewer approves."** Have the agent propose candidates (dead code, unused config, redundant services, bloated prompts); have a human confirm; measure the complexity chart *decrease*. Automation giveth; automation should also taketh away, on a schedule.

## The simplicity test — for anything, at any time

Before a feature, a service, an agent, a prompt, a YAML layer:

- **What's the simplest thing that satisfies the users?** (If "add a service" is the answer, ask *why not a function? a config? a cron? nothing?*)
- **Can I delete this in six months?** (If removing it would be a project, it wasn't simple.)
- **Who will be on-call for it?** (Include your future AI on-call. It inherits your complexity.)
- **What does this buy that the users can feel?** (If the answer is "nothing you can measure," it's complexity.)

## The honesty clause

Simplicity is not the same as *smallness*; some systems *are* genuinely complex (global payments, multi-region storage, large-model infrastructure). Simplicity is "no complexity beyond what the job requires." Correct wire count beats beautiful wiring every single time.
